# Client guide: how the API behaves (mobile app and web admin)

The machine-readable contract is `openapi/openapi.json` (generated by `backend-api/scripts/export_contracts.py`). This guide
covers the behaviour that a schema cannot express. All paths are under `/v1`. All bodies are JSON. All timestamps are ISO 8601
with a time zone (UTC on the wire); all `date` values are plain `YYYY-MM-DD` in the **family's** time zone.

## Errors

Every non-2xx response has the same body:

```json
{"error": {"code": "pin_locked", "message": "...", "request_id": "…", "retry_after_seconds": 900}}
```

`code` is stable and machine-readable (`errors/errors.yaml`); `message` is for logs, not for display. Extra fields depend on the code:
`validation_error` has `details: [{loc, msg}]`, `content_invalid` has `problems: [string]`, `pin_invalid` has `attempts_remaining`,
`pin_locked` has `retry_after_seconds`. Send `X-Request-Id` (any string up to 64 characters) to correlate a client log line with the
server log; the server echoes it. Endpoints listed under the tag "planned (not implemented)" return **501** `not_implemented`.

## Sign-in and tokens

* `POST /auth/signup` and `POST /auth/login` return `{access_token, refresh_token, expires_in, user, memberships[]}`.
  The access token lives 15 minutes, the refresh token 30 days.
* `POST /auth/refresh {refresh_token}` **rotates**: it returns a new pair and the old refresh token stops working. Presenting an old,
  already-rotated refresh token revokes the whole chain (treat as theft), so store the new token before using it and never retry a
  refresh with an old value. If refresh answers 401, sign the user out.
* Send `Authorization: Bearer <access_token>` on every call. On a 401 with `unauthenticated`, refresh once and retry the request once.
* `GET /me` returns the user, family memberships (with `guardian_verified`) and `pin_set`. `user.platform_role` is `null` for families and
  `content_admin` / `super_admin` for staff (only those can call `/admin/*`).

## Guardian verification and consent (India, DPDP Act)

A child profile cannot be created until a guardian has been verified (`403 guardian_verification_required`).
1. `POST /families/{id}/guardian-verification {phone}` sends a 6-digit code by SMS and returns `{verification_id, expires_in}`.
   (In `dev` the response also contains `dev_code`, and in `nonprod` the code is written to the server log.) Limit: 5 per hour.
2. `POST /families/{id}/guardian-verification/confirm {verification_id, code, declaration_accepted: true, notice_version}` where
   `notice_version` must equal `GET /config` → `declaration_notice_version`. On success the core-service consent is recorded.
   Five wrong codes invalidate the verification; start a new one.
3. `GET/PUT /families/{id}/consents` for the optional purposes (`media_capture`, `ai_personalization`, `product_analytics`).
   Consent history is append-only. `core_service` cannot be withdrawn here.

## Parent PIN and child mode

A child never has credentials. The parent signs in; the app then uses two kinds of token:

* **Parent token** (the access token): full access to the family.
* **Child token**: `POST /children/{childId}/sessions {device_id}` → `{child_token, expires_at, child}`. It is valid for 60 minutes, works
  only for that child and can play activities (`GET /activities…`, `/children/{id}/today|plan|history`, `/sessions…`) but cannot call parent
  endpoints (403/404). When it expires (401) the app, still holding the parent token, silently opens a new child session. Use a stable
  per-install random `device_id` (8–100 characters).
* **PIN elevation** guards sensitive actions: `PUT /me/pin {pin, current_pin?}` (4–6 digits), then `POST /me/pin/verify {pin}` →
  `{elevation_token, expires_in: 300}`. Send it as header `X-Elevation-Token` on: `DELETE /children/{id}` and
  `DELETE /children/{id}/sessions` (leave child mode; also revokes the child tokens). Without it: `403 elevation_required`.
* If a PIN already exists, `PUT /me/pin` without `current_pin` answers `409 pin_already_set`: refresh `GET /me` (`pin_set` is then true) and show the PIN entry (or "Forgot PIN?") instead of the first-time form.
* Lockout (`429 pin_locked`, `retry_after_seconds`): 5 wrong PINs → 15 minutes, 10 → 1 hour, 15 → 24 hours; every further wrong PIN
  after the 5th locks again. `POST /me/pin/reset {password, pin}` resets the PIN using the account password (also clears the lock).
* The app should require the PIN (client side, then obtain an elevation token) whenever the user leaves child mode for parent screens.

## Versioning and idempotency

* Records that can be edited from two devices carry `version` (children, plan items). `PATCH` needs the version you last read and answers
  `409 conflict` if it moved; reload and retry.
* `POST /sessions {child_id, activity_id, plan_item_id?, client_op_id}`: `client_op_id` is a UUID generated **on the device**. Repeating the
  call returns the same session (200 instead of 201). Use it for retries and offline queues.
* `POST /sessions/{id}/submit` is idempotent too: a second submit returns the stored result unchanged.
* `occurred_at` on submit and observations must be within the last 7 days (and not in the future) so an offline device can sync later
  without breaking streaks; otherwise 422.

## Activities and the player

`GET /activities` (published only; filters `subject`, `level`, `interest`, `q`, `limit`, `offset`) and `GET /activities/{id}` return
the definition **without answer keys**. Definition shape: `schemas/activity-content.schema.json` (the server also stores format v2 documents, `docs/activity-format-v2.md`, but always sends this shape). Answers are always scored on the server.

| step `type` | what the client shows | answer value sent in `answers[step_id]` |
|---|---|---|
| `instruction`, `media_prompt` | text / caption (+ `alt_text`), no input | none |
| `single_choice` | radio list of `options[{id,label}]` | option id (string) |
| `multi_choice` | checkbox list | list of option ids |
| `numeric_input` | number field | number |
| `short_text` | text field (`max_len`) | string |
| `sequence_order` | reorderable list of `items[{id,label}]` | list of item ids in the child's order |
| `match_pairs` | pair `left[]` with `right[]` | list of `[left_id, right_id]` |
| `timer_task` | countdown of `duration_sec` (+ optional `checklist`) | none (or `true` when done) |
| `reflection` | pick one of `emoji_options` | the chosen emoji string |
| `audio_record`, `photo_evidence` | MVP: explain it is done with a grown-up, allow "Done / skip" | none |
| `parent_checklist` | **not shown to the child**; rated by a parent after submit | none |

Any step, option, item or match member may also carry `image: {asset, alt, sha256, width, height, missing?}`; the definition then has
a top-level `images` manifest (`id, url, sha256, bytes, width, height, content_type`). Download and cache by `sha256`, show the text when a
picture is unavailable, never block an exercise on a picture (details in `activity-format-v2.md`, "Images").

`hint` (optional on any step): a "Hint" button; every use increases `hints_used`. `parent_assist: true` when a grown-up helped.
Flow: `POST /sessions` → optional `PUT /sessions/{id}/autosave {answers, hints_used, parent_assist}` (merges, ignores nothing but rejects
unknown step ids) → `POST /sessions/{id}/submit {answers, hints_used, parent_assist, duration_sec, occurred_at?}` → response `SessionOut`
with `result: {score (0..1|null), scored_steps, steps: {id: {score}}, needs_review: [step ids], independence, skills[]}`.
For each id in `needs_review` the parent later calls `POST /sessions/{id}/review {ratings: {step_id: trying|with_help|independent},
parent_assist?}` (parent token only; can be repeated). `GET /children/{id}/history` lists finished sessions and which still need review.

## Planning, progress, recommendations

* `GET /children/{id}/library?subject=&q=&limit=&offset=` is the parent's Activity library for one child: published activities in the subject whose 
  level range includes the child's level (every level when the child has none), each with `times_done`, `last_done_at` and `planned_for` (the next planned day), 
  activities not yet done first. Add one with `POST /children/{id}/plan/items`.
* `GET /children/{id}/plan?week_start=` (any date; the week starts Monday), `GET /children/{id}/today`, `POST /children/{id}/plan/items`,
  `PATCH|DELETE /plan-items/{id}`. Statuses: `planned → in_progress → completed`, or `skipped`.
* `GET /children/{id}/mastery[?subject=]` (parent): skills with `status` `emerging|developing|secure`, `score` 0..1, `confidence`,
  `needs_revisit`. `POST /children/{id}/observations` (a parent rates a skill), `POST /children/{id}/baseline` (starting checklist).
* `GET /children/{id}/progress/overview[?range_start&range_end]` (defaults to the current week), `GET /children/{id}/dashboard`
  (overview + today + 3 recommendations), `GET /children/{id}/recommendations?limit&max_minutes`.
* Curriculum: `GET /curriculum/levels|subjects|interests|skills`.

## Textbook progress (boards, books, lessons)

Activities can be placed in the lessons of textbooks; a textbook belongs to a board (CBSE, ICSE, ...). An activity can sit
in several books, so `ActivityDetail.placements` is a list. Boards are data, never hard-coded in a client.

- Catalogue: `GET /v1/curriculum/boards`, `GET /v1/curriculum/books?board&grade&subject`, `GET /v1/curriculum/books/{code}`.
  `/v1/activities` and the child library also accept `board` and `book` filters.
- Enrolment (parent): `PUT /v1/children/{id}/books/{code}` (idempotent, returns the path), `DELETE` to leave a book,
  `GET /v1/children/{id}/books` to list enrolments. A newly enrolled child starts with the first lesson that has activities
  unlocked.
- Path: `GET /v1/children/{id}/books/{code}/path` lists lessons in textbook order with their activities and states
  (`not_started`, `attempted`, `passed`). **Soft lock:** a child token never receives the activities of locked lessons; a
  parent token sees everything (locked lessons are marked) and can still plan or open any activity.
- Finished means submitted with a score of at least the pass score (default 0.6, server setting `lesson_pass_score`);
  activities without a score pass once submitted. Finishing below the pass score is `attempted`.
- Unlock (parent): `POST /v1/children/{id}/books/{code}/unlock-next` with `{"force": false}` opens the next lesson, skipping
  lessons that have no activities. If an unlocked lesson is still open it answers 409 `lesson_incomplete`; the parent can
  repeat with `{"force": true}`. With no more lessons it answers 409 `conflict`.
- Child home: `GET /v1/children/{id}/next-up?limit=` returns the next unfinished activities in textbook order across the
  child's books.
- Staff: `GET`/`PUT /v1/admin/activities/{id}/lessons` read and replace an activity's lesson links (`order` is the place inside
  the lesson; 422 on an unknown lesson). Admins reach any activity; an educator their own drafts and the drafts an admin assigned to them (404
  otherwise, 409 `activity_locked` once submitted).

## Daily activities chosen by LearnNest (plan mode)

A family is in one of two modes: `plan_mode` on the family is `parent` (the parent plans by hand, as before) or `system`
(LearnNest releases the activities each day). Read it from `GET /families`. New families start in the mode the
server is configured for; an operator switches a family with the server command `set-plan-mode`.

- The child carries `board_code` and `grade` (set them on create or `PATCH /children/{id}`; the child follows books only when both are set). In system
  mode the child follows every active textbook of that board and grade and the books follow the standard automatically.
- `POST /children/{id}/daily/sync` (child or parent token) is called when the app opens or returns to the front. It
  releases today's set when the rules allow and always answers `{reason, released[], progress, plan_mode}`. At most one set
  is released per local day (family time zone); calling again returns the same set (`already_released_today`).
  Reasons: `released`, `already_released_today`, `below_threshold`, `too_many_open`, `no_content`, `paused`,
  `not_a_school_day`, `no_books`, `not_system_mode`.
- A new set is released when at least `release_threshold` (default 70 %) of the last set is done (finished or skipped), the
  child is not carrying more than `max_open_items`, today is a school day and the child is not paused. Parent grading
  never blocks the next set. Activities are taken from each textbook in turn, in textbook order (lesson, then the
  activity's `order` in the lesson), never twice; settings are per board and grade (see the admin section).
- `GET /children/{id}/daily/status` returns the same `progress`: `{set_released_on, done, total, ratio, threshold, more_needed,
  open_items}` for "x of y done, z more to unlock tomorrow's activities". `PUT /children/{id}/daily/pause {paused_until}` (parent)
  pauses releases until that date (null resumes); a past date is 422.
- `GET /children/{id}/today` returns today's items plus open system or practice items from earlier days (`carry_over: true`).
  Plan items now carry `source` (`parent`, `system`, `revision`), `released_on`, `book_code`, `lesson_position`, `lesson_title`.
- In system mode a parent can no longer plan: adding items, moving or deleting released items, enrolling or leaving
  books and unlocking lessons answer **403 `plan_managed`**. A parent can still skip or un-skip a released item and
  can take back a practice item. Viewing is always allowed. Practice (below) is the one way a family adds activities.

## Results and practice

Reads for a child (own token) or a parent. The page is built from finished sessions; nothing here changes the daily release.

- Scores: an attempt's score is the parent-reviewed score once the parent has rated checklist steps (`reviewed_score` = the
  auto scores and the ratings averaged together, ratings trying 0.3, with_help 0.6, independent 1.0), otherwise the auto
  score. A bucket's score is the mean of each activity's **best** score, so practising again raises it; the mean of the latest
  scores is next to it. Activities with no scoring count as done but are left out of the mean. A week is Monday to Sunday in
  the family's time zone. `pass_score` (0.6) and `strong_score` (0.85, from the release settings) come with the response.
- `GET /children/{id}/results/summary?group_by=subject|week|subject_week|month|lesson|skill&from=&to=&subject=&book=`
  returns `buckets` with activities, attempts, `avg_best_score`, `avg_latest_score`, minutes, `independent_pct`, hints,
  `waiting_review`, `needs_attention`, `previous_score` and `trend` (`up|flat|down`). Default range: the last 8 weeks; time
  groupings start on a whole week or month; at most 400 days; week/month buckets are newest first. Labels for `week` and
  `month` are the ISO key: the client formats them.
- `GET /children/{id}/results/activities?week_start=&from=&to=&subject=&book=&lesson=&attention=&limit=&offset=`: one row per
  activity with `first_score`, `latest_score`, `best_score`, attempts, `status` (`passed|attempted|unscored|waiting_review`)
  and `needs_attention`. Use `subject` with `week_start` for the subject-week list.
- `GET /children/{id}/results/activities/{activity_id}`: all attempts, newest first (score, `reviewed_score`, duration, hints,
  assist, steps waiting for review).
- `GET /children/{id}/results/attempts/{session_id}`: per-exercise result (prompt, the child's answer, right or wrong, feedback
  text, skills, rating). `correct_answer` is sent to a **parent token only**; a child token receives `null`.
- `POST /children/{id}/practice {activity_ids[1-10], scheduled_date?}` (201) puts finished activities, or related ones (same
  lesson or skill), back into the plan as `revision` items, with `skipped[]` reasons: `not_published`, `not_allowed`,
  `already_open`, `cooldown` (not before the cooldown after it was last finished), `cap_reached`, `daily_limit` (child token
  only). A child may add for today only; a parent up to 14 days ahead. Practice items show in Today with a "Practice" tag and
  never count toward the 70 % test.
- `GET /children/{id}/practice/suggestions?limit=` lists what is worth practising: below the pass mark, then weak skills, then
  the same lessons, each with `reason`, `best_score` and `open_in_plan`.

## Admin (platform staff only)

`GET /admin/stats`, `GET /admin/activities[?status&subject&q]`, `GET|PUT /admin/activities/{id}[/definition]`,
`POST /admin/activities/{id}/status {status}` (draft → in_review → published → archived), `POST /admin/content/bundle`
(`dry_run` defaults to true). Admin accounts cannot read any family or child data.

### Assignments (admin hands a draft to an educator)

An admin (`content_admin`, `super_admin`) assigns an existing **draft** to an educator with written requirements and an
optional due date; the educator is emailed and works on the draft with the normal activity endpoints.

- `POST /admin/activities/{id}/assignments {educator_id, requirements (1-4000 chars), due_date?}` → 201
  `{assignment, email_sent}`. 409 if the activity is not a draft, the educator is disabled, or it is already assigned to
  that educator; 404 if the person is not an educator; 422 for a blank brief or a due date in the past. Assigning a draft
  that someone else holds cancels the earlier assignment (kept as history) and moves access to the new educator. An
  email that cannot be sent never blocks the assignment (`email_sent: false`).
- `GET /admin/assignments[?status&live&educator_id&overdue&activity_id&limit&offset]`: admins see everyone's, educators
  only their own (`educator_id` is ignored for them). `GET /admin/assignments/{id}` (404 for another educator's).
- `PATCH /admin/assignments/{id} {requirements?, due_date?}` (send `due_date: null` to remove it) and
  `POST /admin/assignments/{id}/cancel`: admins only, while the assignment is live (open or submitted); 409 otherwise.
- Status follows the activity: `open` (with the educator) → `submitted` when they submit it → back to `open` when it is
  returned (the reviewer's note is on `review_note`) → `completed` when published; `cancelled` when withdrawn,
  reassigned or archived. `overdue` is true for an open assignment past its due date (calendar days, IST).
- An educator reaches an assigned draft while the assignment is open, submitted or completed; cancelling or reassigning
  removes the access. Activity summaries carry `assignment_id`, `assigned_to`, `assigned_to_name`, `assignment_due`.
- Capabilities: `assignments.view_own` (educator) and `assignments.manage` (admins) on `GET /admin/me`.

### Release settings, coverage and preview (admin)

- `GET /admin/release-policies` (any admin) lists the settings rows: the default (`scope_board` and `scope_grade` empty), a
  board, or a board and grade. The most specific row applies to a child. `PUT /admin/release-policies?board=&grade=` (super admin)
  creates or replaces a row: `release_threshold` (0-1), `set_minutes`, `set_max_activities`, `max_open_items`, `school_days`
  (ISO weekdays 1-7), `strong_score`, `revision_open_cap`, `revision_cooldown_days`, `child_daily_practice_limit`. A grade needs a
  board (422); `DELETE` removes an override (the default cannot be removed).
- `GET /admin/coverage?board=&grade=&target_per_lesson=` shows, per active book, lessons with published activities, lessons
  below the target, minutes, `days_of_content` at the current pace and the weakest lessons.
- `POST /admin/release-preview {board_code, grade, days}` lists what a new child would get over the next days if every set is finished.
